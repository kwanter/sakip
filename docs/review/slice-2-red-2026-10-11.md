## Source-supported boundaries

The active User assignment endpoints accept a plain `Request` and authorize
only the protected-account target restriction added in Slice 1. The existing
`UpdateRolesRequest` and `UpdatePermissionsRequest` require the corresponding
UserPolicy assignment ability, which requires `manage-roles`, but these requests
are not wired into those active endpoints.

`AdminService::assignRoles()` and `assignPermissions()` protect Super Admin
targets, but do not enforce assignment authority or the actor's effective
permission ceiling. `createUser()` calls the same role-assignment sink inside
its transaction when the request includes roles.

`RoleManagementController` already requires `manage-roles`. Its role creation
and permission synchronization paths nevertheless accept permissions absent
from the actor's effective permission set. The existing Super Admin role grant
filter remains a separate control and is not removed or bypassed by these tests.

## Disposable fixtures and prerequisites

The new test class disables its own default seeding, creates all named permission
records with `findOrCreate`, and creates verified users and ordinary roles
explicitly. These fixtures support both seeded and unseeded suite baselines.
Every case checks SQLite, the memory database, verification, route permissions,
absence of the Super Admin role, and absence of the sensitive permission.

The user-manager actor initially has `admin.dashboard` and `manage-users`,
but lacks `manage-roles`. Its ordinary baseline role conveys
`admin.users.export`; the actor holds that permission indirectly, not directly.
For the limited-assignment cases, the actor additionally receives `manage-roles`
and both UserPolicy assignment abilities are verified as allowed before the
request. Neither ordinary actor possesses `manage-permissions`.

The ordinary target has `admin.dashboard` and the baseline role. Existing grants
are snapshotted before requests so denied operations must leave them unchanged.
All records are real SQL/Spatie fixtures. No authorization, database, HTTP,
permission synchronization or audit sink is mocked.

The Super Admin positive control deliberately uses a disposable reserved role
with no explicit permissions. This proves its intended Gate bypass while also
working when earlier test classes have seeded that role with permissions.
The test transaction restores the baseline after each case.

## HTTP abuse cases and observed evidence

All submitted IDs exist, all arrays are valid, all creation names/emails are
unique within their fixtures, and update/create requests assert that no
validation errors occurred. The following failures are security assertions,
not unrelated 500/422 responses, fixture failures or absent methods.

| Boundary | Cases | Observed vulnerable behavior |
| --- | --- | --- |
| No assignment authority; sensitive grants | 4 | Direct/role grants persist |
| No authority; owned permissions only | 4 | Unauthorized grants persist |
| Effective permission ceiling, user grants | 4 | Unowned permissions granted |
| Effective ceiling, existing role edit | 2 | Existing members gain authority |
| Effective ceiling, role creation | 1 | Privileged role is inserted |
| User creation with unauthorized roles | 2 | Account and grants inserted |

The User assignment cases cover both the actor itself and another ordinary
target, using direct permissions and role membership. The four authority-only
cases request exclusively permissions already held by the actor; a ceiling
check alone cannot make these tests pass.

The sensitive mixed requests are:

- `POST /admin/users/{target}/permissions`: IDs for `admin.dashboard`,
  `manage-users`, `admin.users.export`, and absent `manage-permissions`.
- `POST /admin/users/{target}/roles`: an allowed role conveying held permissions
  and a different ordinary role conveying absent `manage-permissions`.
- `POST /admin/roles/{role}/permissions`: IDs for `admin.dashboard`,
  `manage-users`, and absent `manage-permissions`; the role is held by the
  actor or by the other target, depending on the dataset.
- `POST /admin/roles`: a unique ordinary role name, `guard_name=web`, and IDs
  for held `manage-users` plus absent `manage-permissions`.

The user-creation cases call `POST /admin/users` with valid identity, institution,
password and confirmation fields. One manager lacks assignment authority but
requests an allowed role. Another has assignment authority but requests both
the allowed and excessive roles. Both must reject the whole transaction.
Currently both insert the account, role grants and successful mutation audit.

For direct/role assignment and existing-role edits, the sensitive access probe
is `GET /admin/permissions`. It is confirmed **403 before mutation**. After
the mutation, the test clears Spatie's permission cache, reloads the target,
and makes another real HTTP request. It becomes **200**. The target still lacks
the Super Admin role, so the escalation is through ordinary permissions.

The composite security assertion collects persisted grants, effective permission,
HTTP probe status, mutation status and, for User mutations, audit changes before
it fails. Thus a first response assertion cannot hide the persistence evidence.

Representative direct-assignment failure:

```text
Expected:
  direct_permissions_unchanged = true
  sensitive_permission_granted = false
  subsequent_http_status = 403
  assignment_http_status = 403
  successful_audit_added = false
Observed:
  direct_permissions_unchanged = false
  sensitive_permission_granted = true
  subsequent_http_status = 200
  assignment_http_status = 302
  successful_audit_added = true
```

Role-assignment failures show changed role membership; role-edit failures show
changed role permission IDs. Role creation stores the excessive permission.
The unchanged-state assertions require rejection of the entire mixed grant;
silently accepting only its allowed portion would still fail.

## Passing controls and strongest counterevidence

Nine positive/control cases pass:

- Two allowed direct-permission subsets and two allowed role grants succeed
  for self/other targets. The indirect `admin.users.export` authority is accepted,
  exact persisted grants are checked, audits remain enabled, and subsequent
  User-index HTTP requests succeed after clearing the permission cache.
- Allowed role creation, permission edits and an empty permission-removal array
  succeed. Both manager and other target are members; removing the grant revokes
  the other target's previously working User-index access.
- Super Admin can grant authority beyond its explicit permissions through User
  assignment, role creation and role editing.
- A manager without assignment authority can still update an ordinary identity
  and create an ordinary account without roles.
- Role creation and role-permission endpoints already reject a manager lacking
  `manage-roles`, with existing grants preserved. This confirms those endpoints
  have an authority guard; their separate problem is the permission ceiling.

All 25 Slice 1 and existing reserved-role tests pass in the sibling run.
Architecture and FloorGuard checks also pass. No live production exposure or
tenant-isolation claim is inferred from these disposable HTTP reproductions.
