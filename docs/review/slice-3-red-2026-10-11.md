## Source-supported root cause

`RoleManagementController::update()` checks administrative route permissions
and uniqueness, but permits renaming both the existing reserved role and an
ordinary role into the newly available reserved name. Its request also accepts
`guard_name`, allowing a non-Super-Admin to mutate the reserved namespace.

`store()` and `updatePermissions()` now apply the Slice 2 permission ceiling,
but that ceiling does not reserve the privileged role identity. Requests with
empty permissions or permissions already held by the actor can still create
or mutate the reserved role.

`AppServiceProvider` grants the Super Admin Gate bypass based on role name.
`InstansiScope` likewise grants its global-access exception based on
`SystemRoles::SUPER_ADMIN`. Changing an existing membership's role name can
therefore activate both bypasses without any role assignment or permission
increase. The delete endpoint already rejects deletion of the reserved name;
that existing control is tested and preserved.

## Disposable fixture prerequisites

The class uses real SQL, Spatie grants, HTTP middleware and controller actions.
Its own seeding is disabled, while `findOrCreate` for shared permissions and the
reserved role supports both seeded and unseeded suite baselines.

Each case creates two institutions, one indicator per institution, and a verified
ordinary role manager in the first institution. The manager holds
`admin.dashboard`, `manage-users`, `manage-roles`, and the policy's actual
`view performance indicators` permission. Its own ordinary role has no grants.
The sensitive `manage-permissions` record exists but is not granted to it.

The reserved role is a controlled disposable fixture with only `manage-users`.
The manager therefore satisfies the Slice 2 ceiling for every tested permission
payload. No reserved-role test fails merely because the actor lacks route
authority, has an unverified email, or requests an absent permission record.

Every case verifies these HTTP prerequisites before mutation:

- Own indicator's performance-data JSON endpoint returns 200 with the correct ID.
- Foreign indicator's corresponding endpoint returns 404.
- Administrative permission management returns 403.
- The actor has neither the Super Admin role nor explicit `manage-permissions`.

The tenant probe is the implemented
`GET /sakip/api/indicators/{indicator}/performance-data?year=2026` route.
It exposes indicator metadata in a real JSON response, even with an empty
performance-data collection. No scope, authorization, Gate or sink is mocked.

## Two-request exploit evidence

The principal TEST-006 case performs both requests through HTTP:

```text
PUT /admin/roles/{existing reserved role}
name = Slice 3 Released Reserved Name
guard_name = web

PUT /admin/roles/{manager's existing ordinary role}
name = Super Admin
guard_name = web
```

Both requests currently return **302**, without validation errors. After cache
clearing and reloading the actor, the test observes:

| Security assertion | Observed vulnerable state |
| --- | --- |
| Original reserved name stays unchanged | Original role renamed away |
| Actor's ordinary role name stays unchanged | Its name becomes Super Admin |
| Actor remains non-Super-Admin | `hasRole(SUPER_ADMIN)` becomes true |
| Permission endpoint remains 403 | It returns 200 |
| Foreign indicator remains inaccessible | Its JSON endpoint returns 200 |
| Foreign ID and sentinel name stay undisclosed | Both appear in JSON |

Before the composite security assertion fails, independent assertions confirm
that the actor's **role IDs and effective permission IDs are unchanged** and
`hasPermissionTo('manage-permissions')` remains **false**. The new access
therefore results from the role name activating Gate/tenant bypass, rather than
an untested permission grant or direct assignment of Super Admin.

Representative assertion output:

```text
Expected:
  actor_became_super_admin = false
  release_http_status = 403
  claim_http_status = 403
  sensitive_http_status = 403
  foreign_http_status = 404
  foreign_indicator_disclosed = false
  foreign_name_disclosed = false
Observed:
  actor_became_super_admin = true
  release_http_status = 302
  claim_http_status = 302
  sensitive_http_status = 200
  foreign_http_status = 200
  foreign_indicator_disclosed = true
  foreign_name_disclosed = true
```

The test gathers persisted names, privilege status and subsequent HTTP outcomes
before failing its composite assertion. An early status assertion cannot hide
the name mutation or cross-institution disclosure.

## Other RED cases

| Case | Count | Persisted evidence |
| --- | --- | --- |
| Release/reclaim chain through HTTP | 1 | Name-based privilege takeover |
| Rename own role into an available name | 1 | Super Admin and foreign access |
| Create the available reserved role | 1 | New reserved role inserted |
| Rename reserved role away | 2 | Name changes, including Super Admin actor |
| Change reserved guard as an ordinary manager | 1 | `web` changes to `api` |
| Set or clear reserved permission grants | 2 | Original permission IDs change |

There are **eight expected security failures**. None is a fixture, validation,
missing-method or unrelated 500 error. Every vulnerable mutation returns 302.

The two available-name tests establish that state by renaming the disposable
reserved fixture before the attack. This prevents a uniqueness 422 from masking
the missing reserved-name rule. That setup is not itself the HTTP exploit proof;
the separate two-request case proves the complete release/reclaim chain without
fixture assistance to release the name.

The non-Super-Admin permission-edit cases explicitly verify that
`grantPermissions` already allows their set/empty payloads. Their persisted
mutations isolate reserved-role protection from Slice 2's ceiling.

The Super Admin rename-away case demonstrates the additional DEC-003 invariant:
even an authorized Super Admin must not destroy the name on which its Gate
bypass depends. Currently it can rename the role and loses its own Super Admin
status. A future guard must preserve this invariant despite the global bypass.

## Passing controls and strongest counterevidence

Seven controls pass:

- An ordinary role can be renamed without changing the actor's authority or
  enabling access to the foreign indicator.
- Authorized ordinary role creation, permission editing and deletion work.
- Both ordinary managers and Super Admin actors are already prevented from
  deleting the reserved role. The role, member IDs and permission IDs survive;
  its existing redirect-with-error response is preserved.
- Super Admin may legitimately set or clear reserved role permissions, retains
  the reserved identity, and can still read the foreign indicator afterward.
- Legitimate Super Admin access to the foreign JSON endpoint returns 200 with
  the expected ID and sentinel name, proving the tenant probe works normally.

All 64 sibling cases from Slices 1/2 and the original reserved-role assignment
tests remain green. Architecture and FloorGuard checks also pass. Their guards
do not stop a role name change because the attack leaves membership IDs and
permission grants unchanged.
